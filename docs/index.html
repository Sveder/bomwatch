Know what got installed on your machine.

bomwatch keeps a software bill of materials for the machine it runs on, and tells you when new software appears. It was built for machines where AI agents run pip install, npm i -g and curl | sh on their own.

Why this exists

Coding agents now install software as part of their normal work. They add a dependency to fix a test, pull a CLI to try it, download a binary from a release page. Most of the time that is fine. But nobody keeps a record, and the tools we have look somewhere else.

  • Supply-chain scanners watch the repo. They check the lock file in a pull request. An agent that runs pip install in a scratch venv, or npm i -g, never touches a lock file.
  • Install-time firewalls watch one path. They wrap npm or pip. They don't see apt, docker pull, a Steam game or a zip unpacked in ~/Downloads.
  • Fleet agents watch everything, at a cost. osquery and endpoint tools answer these questions, but you run a daemon, write queries and ship logs somewhere.
  • bomwatch looks at the machine itself, after the fact. Whatever path software took, it ends up on disk. bomwatch reads what is there, from package databases and metadata files.
  • It keeps a history. Every scan is a small JSON file, so diff and log can tell you when something appeared, even if a collector failed in between.
  • It's small and local. Python standard library only, no daemon, no account. Nothing leaves the machine unless you ask for a vulnerability lookup.

What it does

One command lists everything, from system packages to games. The next one tells you what changed.

bomwatch scan

20 collectors, one list

dpkg, rpm, snap, flatpak, Homebrew, pip envs, npm (global and per project), cargo, go, docker, podman, editor extensions, Steam, loose programs, macOS apps and Windows installs.

bomwatch diff

No false alarms

Versions are compared the way each ecosystem does it (Debian, RPM, PEP 440, semver). A collector that failed or was skipped is left out of the comparison, so its packages are never reported as removed.

--vulns

Known vulnerabilities

New versions are looked up on osv.dev: PyPI, npm, crates.io, Go, and Debian and Ubuntu packages by their source package. Exit code 4 means something vulnerable came in.

bomwatch export

CycloneDX and SPDX

Every package gets a package URL (purl), so you can load the machine's SBOM into Dependency-Track, Grype or your own tooling.

bomwatch watch

Continuous watch

Scan every few minutes, print each change as it happens, save a snapshot only when something changed. It comes with systemd units and a Windows scheduled task.

bomwatch log NAME

History of one package

When did jinja2 first show up in that venv, and when did it change? log reads all saved scans and tells you.

bomwatch never runs a program it finds. The version of an .exe is read from its version resource, straight from the file. The same goes for Python envs: their metadata files are read, and their interpreters are never started.

How it compares

These are good tools, and bomwatch is meant to sit next to them, not replace them. The difference is the question each one answers.

ToolQuestion it answersWhere it looksHow bomwatch differs
bomwatchWhat is installed on this machine, and what is new since the last scan?The machine: package databases, envs, app folders, the registry—
SocketIs this open source package safe to install?Dependencies in pull requests and at install time, through a GitHub app, CLI and firewallSocket judges packages before they come in, with deep behavior analysis. bomwatch records what did come in, by any path (apt, a Steam game, a binary in Downloads), after the fact and without an account. Use Socket to block bad packages, and bomwatch to see everything that landed.
SyftWhat is inside this image or directory?A container image or a filesystem, onceSyft knows more language ecosystems and makes great one-off SBOMs. bomwatch keeps the history and the diff, and covers apps and Windows installs.
OSV-Scanner, Trivy, GrypeDoes this project or image have known vulnerabilities?Lock files, SBOMs, imagesbomwatch uses the same OSV data, but for the software on the machine, and only for what just changed if you like. You can also hand them a bomwatch export.
Dependabot, SnykAre this repo's dependencies out of date or vulnerable?Manifests in a repositoryA repo scanner doesn't see the scratch venv or the global npm install an agent made outside the repo.
osqueryAnything about the host, in SQLThe machine, through a daemonosquery is more powerful and meant for fleets. bomwatch is one command with no daemon, and a diff that works out of the box.
AIDE, TripwireDid any file change?File hashesThose tools see files, not packages. bomwatch tells you "jinja2 2.10 in ~/proj/.venv", not "400 files under site-packages".

Get started

You need Python 3.10 or newer, on Linux, macOS or Windows. There are no other dependencies.

git clone https://github.com/Sveder/bomwatch.git
cd bomwatch
python3 -m venv .venv && . .venv/bin/activate
pip install -e .

bomwatch scan
# ... later ...
bomwatch scan && bomwatch diff --vulns

Exit codes make it easy to script:

0 no changes 1 error 2 usage 3 changes 4 vulnerable

Run it all the time with bomwatch watch, a systemd timer from contrib/systemd, or the scheduled task in contrib/windows.

Vulnerability lookups send only package names, ecosystems and versions to osv.dev, and only when you pass --vulns or run bomwatch vulns.
